## 已确认的开发原则

2026-11-15 后续视觉评审：用户要求重做整体页面，并否决后台侧栏、大色块、PPT式界面。当前优先人物、背景和材质的统一，保留 08 人物原造型与比例；完整设计草案见 game-design.md，具体内容提案见 designs/formal-content-draft.json。提案并未自动启用新运行流程。

现有原型是起点和回归样例。教学阶段的功能上限不再作为后续拒绝扩展的依据，正式实现按持续迭代所需的模块边界、存档能力、内容配置、调试和验证考虑。

成熟度通过完整可玩的流程、清楚的职责、可靠的进度保存和可验证的行为建立。系统规模与功能数量按实际玩法需求增长；通用接口以已有复用点为依据，避免业务难以追踪。

此前用户明确确认的玩法继续有效，尤其是每日物资在结算最后扣除，以及风险提示后允许继续修复。固定 A/B 教学路线、第 2 天结束和教学失败完全重置描述当前原型，不自动确定正式版的地图、通关或失败代价。

## 当前实现与正式化差距

下表保留启动本轮重构时的差距记录。当前分层、进度保存、按钮命名与角色接入已发生变化，以 architecture.md、designs/ui/card-component.md 和 refactor-verification.json 为准；其他 UI 与正式版运行规则仍在后续范围内。

| 当前代码事实 | 正式化需要处理的边界 |
| --- | --- |
| `SurvivalGame` 同时管理路线、战斗、背包、日结算和失败重置 | 按实际系统边界拆分规则与状态；用应用层串起完整流程 |
| `ROUTES` 只有 A/B 固定路线，`finishDay()` 直接进入第 2 天终点 | 将教学流程定义与可持续的探索、日循环、结束条件分离 |
| `fail()` 调用全量 `reset()` | 明确一次探索失败、战役进度、永久收藏等不同生命周期，再实现失败与恢复规则 |
| 当前没有查到玩家存档实现 | 设计可序列化状态、版本号、保存时机、读取校验和升级方式；卡牌配置备份不承担玩家存档职责 |

## 建议的实施次序

1. **整理现有核心与边界。** 保留已验证规则，分清配置、单次探索状态、战斗状态、游戏命令和界面表现，将教学流程作为可替换的剧本或关卡配置。
2. **确定持续游玩的完整闭环。** 设计出发、探索、返家、结算、下一次出发及终局条件；同时明确失败后哪些状态保留、哪些丢失。不能只去掉“第 2 天结束”文案就认定日循环完成。
3. **落地进度持久化。** 以明确的数据生命周期设计存档，覆盖继续游戏、异常中断、配置变化及版本升级，保持规则层独立于具体存储平台。
4. **逐项扩展内容系统。** 根据玩法方案增加地图、敌人、事件、卡牌机制和长期成长；数据工具与游戏同步扩展。
5. **持续完善表现与交付。** 规则正确性、交互稳定性、真实引擎资源编辑、性能、异常处理和打包检查随相应功能推进。

这些次序是工程建议，不代表本轮已经实现上述系统。当前 40 条测试和既有浏览器流程可作为后续迁移基线，变更行为时更新相应验收。
